# Зачем нужен Git

## Введение

Вот папка проекта, над которым работали три человека:

```note
проект/
│
├── отчет_финальный.docx
├── отчет_финальный_2.docx
├── отчет_ФИНАЛЬНЫЙ_правки.docx
├── отчет_v3_правки_Саши.docx
└── отчет_ТОЧНО_ФИНАЛЬНЫЙ_НЕ_ТРОГАТЬ.docx
```
Какой из файлов актуальный? Чем «v3_ правки_ Саши» отличается от «ФИНАЛЬНЫЙ_правки»? Что именно поменялось между версиями и можно ли откатить одну правку, не теряя остальные? Ответов нет, потому что сами файлы об этом ничего не знают, а люди уже не помнят.

С кодом эта проблема становится острее на порядок. Проект состоит из сотен файлов, меняются отдельные строчки внутри них, над одними и теми же файлами параллельно работают несколько человек, и любая правка может что-то сломать. Копированием файлов с новыми именами такое уже не вывезти, и ровно для этого существует Git.
 
## Что такое Git

Git – это система контроля версий, то есть программа, которая следит за директорией проекта, запоминает ее состояния и хранит всю историю изменений. Директория под управлением Git называется репозиторием.

Создал Git в 2005 году Линус Торвальдс, тот же человек, который создал Linux. Ему нужен был инструмент для работы над ядром Linux, куда изменения присылают тысячи разработчиков со всего мира, и существующие тогда системы для такой нагрузки не подходили. Сегодня Git стал стандартом индустрии: на нем построены GitHub и GitLab, а в вакансиях DevOps-инженера он идет в требованиях сразу рядом с Linux.

## Коммиты, сохранения для проекта

Главное понятие Git – это **коммит**, сохраненный снимок всего проекта в конкретный момент времени, к которому прикреплено, кто его сделал, когда и зачем (короткое сообщение от автора).

Работает это примерно как сохранение в игре: если дальше все пошло не так, вы возвращаетесь к сохранению и пробуете снова. Разница в том, что сохранения в Git не перезаписываются, а копятся. Каждый коммит остается в истории навсегда, и вернуть проект можно к любому из них, хоть к сегодняшнему утру, хоть к состоянию полугодовой давности.

## История, что именно изменилось

Git хранит изменения построчно. Если попросить его показать разницу между двумя коммитами, ответ будет выглядеть так:

```note
- timeout = 30
+ timeout = 5
```
Строка с минусом удалена, строка с плюсом добавлена. Такой формат называется диффом, и читать его вы научитесь быстро, потому что устроен он логично.

На практике это одно из первых действий, к которому прибегают при неполадках. Сайт упал после обновления, и нужно понять, что именно выкатили, поэтому открываем последние коммиты и видим каждую измененную строку. В конфиге странное значение, и непонятно, зачем оно там, тогда Git покажет, кто и в каком коммите эту строку написал, а сообщение коммита подскажет зачем. Неделя работы зашла в тупик, и мы возвращаемся к коммиту недельной давности, ничего не потеряв, ведь тупиковый вариант тоже остался в истории.

## Ветки, параллельные версии проекта

Вторая ключевая идея Git – это **ветки**. Ветка – это отдельная линия истории, которая отходит от основной и живет своей жизнью.

Основная ветка обычно называется `main` или `master` и хранит рабочую версию проекта. Когда нужно сделать что-то новое, создается отдельная ветка: все коммиты идут в нее, а `main` остается нетронутой. Когда работа готова и проверена, ветка вливается обратно, и это называется слиянием, по-английски `merge`.

Удобство тут в нескольких вещах сразу. Недоделанная и сломанная работа не попадает в рабочую версию: пока фича не готова, она живет в своей ветке и никому не мешает. Несколько человек работают параллельно, каждый в своей ветке, и не затирают правки друг друга. А эксперименты обходятся даром: если что-то не получилось, ветка просто удаляется, и в `main` от нее не остается ни следа. 

## Причем здесь DevOps

В DevOps Git не ограничивается хранением кода, он встроен в сам процесс доставки.

Пайплайны CI/CD запускаются от событий в Git: разработчик отправил коммит в репозиторий, и это автоматически запустило сборку, тесты и деплой. В репозиториях при этом лежит не только код приложений, но и конфиги серверов, скрипты автоматизации, описания инфраструктуры. У такого подхода есть приятное следствие: откат неудачной настройки превращается в возврат к предыдущему коммиту, а история изменений инфраструктуры становится журналом, по которому потом разбирают инциденты.

Сами репозитории при этом живут не только на компьютерах разработчиков. GitHub и GitLab хранят удаленные копии репозиториев и добавляют к Git совместную работу: обсуждение изменений, проверку чужого кода перед слиянием, управление доступом. GitLab вдобавок умеет запускать те самые пайплайны.

## Git на практике: коммит, ветка, мерж

# Репозиторий за одну команду

Git превращает в репозиторий любую папку. Создадим ее и скажем Git следить за ней:

```bash
mkdir myserver
cd myserver
git init
```
Внешне ничего не изменилось, но команда `ls -la`окажет в папке нового жителя: скрытую директорию `.git` Именно в ней Git хранит всю историю, а сами ваши файлы он не трогает. Папка `myserver` с этого момента и есть репозиторий.

Вторая команда, которую стоит запомнить раньше остальных, – `git status`. Она ничего не меняет, а только отвечает на вопрос «что сейчас происходит»: какие файлы изменились, что готово к коммиту, в какой вы ветке. Прямо сейчас она честно скажет, что коммитить нечего:

```bash
git status
```
Вывод
```note
On branch main
No commits yet
nothing to commit
```
Когда непонятно, что происходит с репозиторием, первым делом смотрят `git status.` Это безопасная команда уровня ls, ее можно дергать сколько угодно.

## Первый коммит

Создадим файл конфига:
```bash
echo "listen 80;" > nginx.conf
git status
```
Вывод
```note
Untracked files:
  nginx.conf
```
Git заметил новый файл, но пометил его как `untracked`: файл лежит в папке, но за его историей Git пока не следит. Чтобы файл попал в историю, нужен коммит, а делается он в два шага:

```bash
git add nginx.conf
git commit -m "Базовый конфиг nginx"
```
Шаг первый, `git add`, отбирает изменения, которые войдут в снимок. Шаг второй, `git commit`, этот снимок сохраняет. Флаг `-m` задает то самое сообщение коммита, о котором шла речь раньше: кто и когда, Git запишет сам, а вот «зачем» остается вашей работой. Сообщение вроде «правки» или «фикс» в будущем не дадут никакой пользы, поэтому пишите так, чтобы по истории можно было читать жизнь проекта.

Зачем два шага вместо одного? Затем, что в реальной работе изменения редко приходят по одному. Вы могли поменять пять файлов, из которых два относятся к настройке портов, а три к логированию. `git add` позволяет отобрать сначала одну группу и закоммитить ее отдельно, потом вторую. Каждый снимок остается осмысленным, и историю потом можно читать как список понятных изменений, а не как свалку «поменял всякое».

История уже существует, посмотрим на нее:

`git log --oneline`

Вывод
`a3f8c21 (HEAD -> main) Базовый конфиг nginx`

Набор букв и цифр слева – идентификатор коммита, по нему к этому снимку можно будет вернуться когда угодно.

## Цикл изменений

Теперь главный ритм работы с Git. Поменяем конфиг:

```bash
echo "listen 8080;" > nginx.conf
git status        # подскажет: modified, nginx.conf изменен
git diff          # покажет, что именно изменилось
```
Вывод
```note
- listen 80;
+ listen 8080;
```

Это тот самый дифф, что мы видели раньше, только теперь он ваш: строка с минусом ушла, строка с плюсом пришла. Привычка смотреть `git diff` перед коммитом спасает от случайных изменений, которые вы не собирались сохранять.

Дальше знакомые два шага:

```bash
git add nginx.conf
git commit -m "Перенес сайт на порт 8080"
git log --oneline
```
Вывод
```note
9b2e110 (HEAD -> main) Перенес сайт на порт 8080
a3f8c21 Базовый конфиг nginx
```
Вот и весь повседневный цикл: **поменял, посмотрел diff, add, commit**. Все остальное в Git надстраивается над этой четверкой действий.

## Ветка без риска для рабочей версии

Сейчас оба коммита живут в ветке main. Допустим, мы хотим попробовать перевести сайт на защищенное соединение, но не уверены, что получится, и трогать рабочий конфиг не хотим. Это ровно та ситуация, под которую придуманы ветки.

Важная деталь: ветка – это не копия директории и не отдельная версия проекта на диске, а легкая метка, указатель на коммит, поэтому ветки создаются мгновенно и ничего не весят. Создадим ветку и сразу в нее переключимся:

`git switch -c ssl-experiment`

Команда `git switch` переключает ветки, а флаг `-c` заодно создает новую. В старых инструкциях ту же работу делает `git checkout`: `git checkout -b` имя и `git checkout` имя. Это более ранняя команда, она умеет много разного; `git switch` добавили позже, и занимается он только ветками. Результат одинаковый. Проверить, где вы находитесь, можно через `git branch`: текущая ветка помечена звездочкой. Теперь экспериментируем:

```bash
echo "listen 443 ssl;" > nginx.conf
git add nginx.conf
git commit -m "Включил SSL"
```
Этот коммит ушел в ветку ssl-experiment, а main остался стоять на месте
И самое наглядное в ветках. Вернитесь в main и загляните в файл:
```bash
git switch main
cat nginx.conf
```
Вывод
`listen 8080;`

Эксперимента в файле нет. Git физически подменяет содержимое рабочей папки под ту ветку, в которой вы находитесь: в main лежит версия main, а если переключиться обратно в ssl-experiment, SSL вернется. Одна папка, несколько параллельных состояний проекта.

## Мерж вливает результат

Допустим, эксперимент удался, и SSL-конфиг должен стать основным. Слияние всегда делается стоя в той ветке, в которую вливают изменения, поэтому сначала переключаемся в main:

```bash
git switch main
git merge ssl-experiment
```
Дальше возможны два сценария. Если main с момента создания ветки не менялся (наш случай), слияние проходит незаметно: Git просто передвигает main вперед, на последний коммит ветки, и никаких новых коммитов не появляется. Если же за время эксперимента в main успели появиться свои коммиты, например от коллеги, Git создаст отдельный коммит слияния, который соединит обе линии истории в одну.

Влитая ветка больше не нужна, удалим ее:

`git branch -d ssl-experiment`

Флаг -d подстрахует: он удаляет ветку только если ее изменения уже влиты, так что потерять работу этой командой не выйдет.

## Конфликты, когда Git просит помощи

Один случай Git не может разрешить сам: обе ветки изменили одну и ту же строку файла по-разному. Скажем, в main кто-то поставил `listen 8080`;, а в вашей ветке та же строка стала `listen 443 ssl`;. Какой вариант правильный, знаете только вы, поэтому Git останавливает слияние и вставляет прямо в файл маркеры с обоими вариантами:

|Вывод			|
|-----------------------|
|<<<<<<< HEAD		|
|listen 8080;		|
|=======================|
|listen 443 ssl;	|
|>>>>>>> ssl-experiment	|

Сверху версия текущей ветки, снизу версия вливаемой. Разрешается конфликт руками: открываете файл, оставляете правильный текст, убираете маркеры, затем `git add` и `git commit`, и слияние завершено. Если что-то пошло не так, `git merge --abort` отменит слияние целиком и вернет все как было.

Выглядит конфликт страшнее, чем есть на деле: Git ничего не сломал и ничего не потерял, он показал два варианта и ждет вашего решения.

## Шпаргалка

Вся практика этого шага умещается в одиннадцать команд:

| Команда               | Что делает                          |
|-----------------------|-------------------------------------|
| `git init`            | превратить папку в репозиторий       |
| `git status`          | показать, что сейчас происходит      |
| `git add файл`        | отобрать изменения для коммита       |
| `git commit -m "..."` | сохранить снимок с сообщением        |
| `git log --oneline`   | история коммитов в одну строку       |
| `git diff`            | что изменилось с последнего коммита  |
| `git branch`          | список веток                        |
| `git switch имя`      | переключиться на ветку               |
| `git switch -c имя`   | создать ветку и переключиться        |
| `git merge имя`       | влить ветку в текущую                |
| `git branch -d имя`   | удалить влитую ветку                 |
