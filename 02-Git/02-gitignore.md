# .gitignore: что нельзя коммитить

## Введение

Вернемся к `git status`. В раннем примере репозиторий был стерильным: одна папка, один файл `nginx.conf`. В настоящем проекте та же команда сразу после `git init` покажет совсем другую картину:

```bash
Untracked files:
  app.py
  .env
  node_modules/
  app.log
  .DS_Store
```
Git честно предлагает взять под контроль все, что нашел в папке. Но в историю проекта должно попасть далеко не все из этого списка. `app.py` – да, это код. А вот `.env` с паролями, гигабайтная папка `node_modules` и лог приложения в истории не нужны, а кое-что из этого там еще и опасно. Разберемся, что отсекать и как сказать об этом Git.

## Что не должно попадать в Git

Лишнее в репозитории делится на несколько понятных групп.

Первое и самое важное – это секреты. Пароли от баз данных, токены доступа, приватные ключи, файлы вроде `.env` с настройками подключения. Это та же категория, что приватный SSH-ключ из модуля про Linux: вещи, которые видеть должны только вы. В общий репозиторий они попадать не должны ни при каких условиях, и почему именно, разберем отдельно ниже.

Вторая группа – то, что генерируется из кода и восстанавливается командой. Папка зависимостей `node_ modules`, каталоги сборки `build` и `dist`, кэши вроде` __ pycache __` . Эти файлы не пишут руками, их создает инструмент по описанию проекта. Хранить их в Git бессмысленно: они весят много, постоянно меняются и в любой момент собираются заново.

Третья группа – мусор и временные файлы. Логи (`app.log`, `*.log`), временные файлы, дампы. Они меняются каждую секунду работы программы, и их история не несет никакого смысла.

И последнее – личные и системные файлы, к проекту отношения не имеющие. `.DS_Store` создает Finder на macOS, `Thumbs.db` – проводник Windows, а папки `.idea` и `.vscode` хранят настройки редактора конкретного разработчика. Коллеге они не нужны, а в истории только шумят.

## Файл .gitignore

Чтобы Git перестал замечать ненужное, в репозиторий кладут файл с именем `.gitignore`. Это обычный текстовый файл со списком того, что Git должен игнорировать: такие файлы не показываются в `git status`, не попадают под `git add` и, значит, не уходят в коммиты.

Обратите внимание: сам .gitignore в историю как раз попадает. Он часть проекта, и правила должны быть одинаковыми у всей команды, поэтому его коммитят наравне с кодом.

## Как пишут правила

Внутри .gitignore идет по одному правилу на строку. Базового набора хватает почти всегда:

```note
# строки с решеткой — комментарии

.env              # конкретный файл по имени
*.log             # любой файл с расширением .log
node_modules/     # целая директория (косая черта в конце)
secrets/          # и эта тоже

```

Имя файла означает именно этот файл. Звездочка * заменяет любую часть имени, поэтому  `*.log` накрывает все логи разом. Косая черта в конце говорит, что речь о директории со всем содержимым. Этих приемов достаточно, чтобы описать почти любой проект, а готовые шаблоны `.gitignore` под конкретный язык легко найти и взять за основу.

## Ловушка, которую .gitignore не закрывает

.gitignore действует только на файлы, которые Git еще не отслеживает. Если файл уже попал хотя бы в один коммит, добавление его в .gitignore не сделает ничего: Git продолжит следить за ним как ни в чем не бывало.

Чтобы перестать отслеживать уже закоммиченный файл, его убирают из-под контроля отдельно:

`git rm --cached .env     # убрать из отслеживания, сам файл на диске оставить`

После этого его еще нужно занести в .gitignore, иначе Git снова предложит его добавить. Но есть нюанс важнее: из прошлых коммитов файл при этом никуда не девается.

## Секреты в истории остаются навсегда

Git тем и ценен, что ничего не забывает, и в случае с секретами это оборачивается против вас. Если пароль или ключ хоть раз попал в коммит, он остается в истории навсегда. Удалить файл новым коммитом недостаточно: старый коммит с секретом по-прежнему лежит в репозитории, и из него все можно достать.

Для публичных репозиториев это не теория. Открытые репозитории постоянно сканируют боты, и выложенный по ошибке ключ, например от облака AWS, находят и пускают в дело буквально за минуты, а со счетом за чужие траты потом разбирается владелец. GitHub даже встроил защиту, которая умеет распознавать секреты и блокировать такой коммит на отправке, но полагаться стоит не на нее, а на привычку не коммитить лишнее.

Поэтому если секрет все-таки утек в репозиторий, чистки истории мало. Единственное надежное решение – отозвать сам секрет: сменить пароль, перевыпустить ключ, сделать утекшее значение недействительным. Тогда даже найденная в истории копия уже ничего не открывает.

## Как держать секреты вне репозитория

Сложилась простая практика. Настоящие секреты держат в файле .env, который занесен в .gitignore и у каждого разработчика свой. А рядом коммитят его шаблон, обычно .env.example, тот же список настроек, но с пустыми значениями:

```note
	# .env  — в .gitignore, с настоящими значениями, в Git не идет
	DB_PASSWORD=s3cr3t-real-password
	
	# .env.example  — коммитится, это шаблон без секретов
	DB_PASSWORD=

```

Так новый человек в проекте видит, какие настройки нужны, но не получает чужих паролей, а сами секреты в историю не попадают. В реальной доставке секреты вообще не лежат в файлах рядом с кодом, а подставляются отдельно, переменными окружения и хранилищами секретов.
